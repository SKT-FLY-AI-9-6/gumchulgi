# psepipe_v3_seam 검증 결과 (2026-08-12)

`psepipe_v3_seam.zip` 을 풀어 검출 정확도·속도·구조를 검증했다.
이 폴더는 zip 내용에 **아래 수정 1건만 적용**한 실행 가능 사본이다.

## 적용한 수정

- `psefield.py`: zip·저장소 어디에도 없는 `pselive3` import 를 제거하고,
  유일하게 쓰이던 `_build_oetf()`(sRGB 역변환 4096-LUT)를 인라인했다.
  이 수정 전에는 `psefield → psepipe → tier` 임포트 체인이 전부
  `ModuleNotFoundError` 로 죽어 사용법.txt 의 1번 명령부터 실행 불가였다.

## 실행 검증 (수정 적용 후)

- `tier.py`: 정상 동작. 위반/안전 판정과 축별 여백 표 출력 확인.
- `psepipe.py v_flash5hz → out.mp4`: 사다리 9단째(chan a0.05 dn3.0)에서 적합
  전환, 출력 파일 독립 재판정도 적합. 6초 클립에 21초(0.28배속).
- `psepipe.py v_stripes → out.mp4`: **아래 버그 2 재현.** 0단이 "적합"으로
  오판 → 파일 재판정에서 `스트림 [] vs 파일 ['패턴']` 불일치 → 최종 출력 여전히
  패턴 위반.

## 수정 2 — 폐루프 패턴 재판정 무력화 (2026-08-12 수정 완료)

증상: `pse_bt1702.analyze` 가 프레임 이터러블을 받으면 메인 루프가 제너레이터를
소진한 **뒤에** `pse_pattern.analyze(path)` 를 불렀다. (a) fps 미전달로
ValueError → `pass: None` 으로 삼켜지거나, (b) fps 를 넘겨도 0프레임을 보고
조용히 통과. 어느 쪽이든 need_B 사다리가 0단에서 "패턴이 고쳐졌다"고 착각해
작동기 B 를 검증·최적화하지 못했다.

수정: `pse_pattern.Stream` (프레임 단위 누적 API) 을 만들고 pse_bt1702 의
메인 루프에서 자기 디코드·축소 프레임(`small`)을 직접 먹인다. 기존
`pse_pattern.analyze(path)` 는 같은 Stream 을 쓰는 래퍼로 유지 — 결과 동일.

검증 (수정 후):
  · 정답 클립 13편 회귀 — 여전히 13/13.
  · v_stripes 를 제너레이터로 재판정 — 수정 전 `[]`(오판) → 수정 후 `['패턴']`.
  · psepipe v_stripes 엔드투엔드 — 사다리 각 단이 정직하게 "위반 패턴" 보고,
    `스트림 vs 파일` 불일치 경고 소멸.
  · 부수 효과: 패턴용 별도 디코드가 없어져 1080p 5초 전체 판정
    5.8s → 4.7s (0.87x → 1.07x 실시간).

## 남은 이슈 (수정 안 함 — 원저자 확인 필요)

1. `PatternFix.min_k=0.25` 하한 때문에 p2t 200cd 줄무늬는 최선이 50cd — 임계
   20cd 를 구조적으로 못 넘는다. 폐루프가 정직해져도 극단 패턴은 B 로 못
   고친다 (위 v_stripes 실측: 전/후 모두 패턴 위반. 이제 그 사실이 루프에도
   보인다는 것이 수정의 효과).
2. `pse_cut.analyze` 는 이터러블 미지원(cut_result 캐시로만 우회 중).
3. 판정기 이원화: psecore(sRGB, psefield.run 사용) vs pse_bt1702(BT.1886,
   psepipe 사용). apply_stream·uv_prime·적색 로직 중복 두 벌 — 드리프트 위험.
4. 성능: 컷 채널은 여전히 별도 디코드 1회 (1080p 5초에 1.2s).
