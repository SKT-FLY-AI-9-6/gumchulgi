### 원인 1 — 컷 판정을 잘못된 도메인에서 쟀다 (수정함)

CPU 기준판 `pselive3._is_cut` 은 **감마 부호화된 8비트 그레이**에서 잰다
(`cv2.COLOR_BGR2GRAY`, Rec.601). GPU 판은 **선형광 Rec.709 루마**에서 쟀고
임계는 CPU 용 `cut_thresh=0.45` / `flat_sd=6.0` 을 그대로 썼다.

감마는 비선형이라 `/255` 환산으로 못 메운다 — NCC 값 자체가 달라진다.
선형광에서는 밝은 프레임의 분산이 과장돼 연속 프레임 상관이 실제보다 낮게 나오고,
그래서 컷이 과검출됐다. **22번 55회.** 컷마다 `prev` 가 리셋되니 시간축 평활이
아예 누적되지 않아 **출력이 원본과 완전히 같아졌다**(6.80s → 6.80s).

수정: 컷 판정만 CPU 와 같은 감마 도메인 Rec.601 그레이(0~255)에서 잰다.
`srgb_eotf` 가 이미 만드는 전해상도 float 중간값을 재사용해 변환을 두 번 하지 않는다.

**프레임 단위 대조** (`harness/cutdiff.py` — 숫자가 아니라 같은 프레임에서
같은 판단을 하는지 본다):

| 클립 | CPU 컷 | GPU 컷 | 일치 | GPU 과검출 | GPU 미검출 |
|---|---|---|---|---|---|
| seg6 | 26 | 27 | 26 | 1 (65번) | 0 |
| 22_game_hud | 0 | 0 | — | 0 | 0 |
| 21_anime_cuts | 0 | 0 | — | 0 | 0 |

수정 후 전수: **일치 25 / 불일치 1 / 악화 1** → `results/verify_full_27_gpu_fixed.txt`
(페더 0 까지 적용한 최종본에서는 seg6 도 0.00 PASS 가 되어 **일치 26 / 불일치 1 /
악화 1** → `results/verify_full_27_gpu_feather0.txt`)

seg6 잔여(0.58s → 0.16s)는 26개 중 한 프레임을 더 잡는 데서 온다. 축소 경로가

속도 비용: **+0.66 ~ +0.77 ms/frame (+4~11%)**. 헛된 컷이 있던 22번은 오히려
**37.8% 빨라졌다**.

### 원인 3 — 14번 악화: 페더링. CPU 는 해결, GPU 는 잔존

`pselive3.py` 헤더 **지뢰 6** 이 이미 지목하고 있었다: `0<A<1` 인 페더 띠의
실제 변화는 `A·k + (1-A)` 라 상한을 넘고, 그 반쯤 처리된 띠가 **넓게 이어지면**
면적 규칙을 그대로 만족시켜 없던 위반이 생긴다.

27클립 전수 스윕 (악화 = 안전한 원본을 위반으로 만든 클립 수):

| 페더 | 알파보정 | 악화 | 남은 위반초 |
|---|---|---|---|
| **5.0** | off ← 기존 기본값 | **1** (14번 0.00→1.54) | 1.54 |
| 2.0 | off | 0 | 0.16 |
| 1.5 | off | 0 | 0.16 |
| **1.0** | off | **1** (0.00→0.94) | 1.06 |
| **0.5** | off | **1** (0.00→1.20) | 1.20 |
| **0.0** | off | **0** | **0.00** |
| 5.0 / 2.0 / 3.0 | on | 0 | 0.00 |

**비단조다.** 1.5·2.0 이 통과하는 건 이 코퍼스에서 우연히 면적 규칙을 안 넘은
것이고, 0 만이 페더 띠라는 기전 자체를 없앤다. (`alpha_smooth` 때문에 시간축
부분 알파는 남으므로 완전한 증명은 아니다 — 새 영상에서 재확인할 것.)

`alpha_compensate=True` 로도 막히지만 마스크 면적이 넓어져 **선명도가 80%→46%**
로 깎인다(01번). 페더 값과 무관하게(2.0·3.0·5.0 전부 46%) 알파보정 자체의 비용이다.
그래서 `feather_px = 0.0` 을 택했다. 대가는 마스크 경계가 딱딱해져 헤일로가
느는 것 (22번 13.0 → 17.5, seg6 43.2 → 47.6).

→ `results/sweep_feather.txt`, `sweep_feather_fine.txt`, `quality_feather*.txt`

**결과: CPU 기준판은 27클립 전부 악화 0** (14번 1.54 → 0.00).
GPU 는 이 단계에서 14번만 1.14 로 남았고, 그건 **원인 4** 로 따로 잡았다.

### 원인 4 — `F.interpolate(mode="area")` 는 `cv2.INTER_AREA` 가 아니다

`GPU_FULL.md` 가 이식 위험 세 곳 중 **첫 번째**로 적어둔 자리다
("축소 `cv2.INTER_AREA` vs `F.interpolate(mode="area")`"). 이름이 같아서
동등하다고 넘어갔는데, **판정을 뒤집는 크기의 차이**였다.

- `F.interpolate(mode="area")` = `adaptive_avg_pool2d` — **정수 경계**로 구간 분할
- `cv2.INTER_AREA` — 0.75 배 같은 비정수 배율에서 **분수 가중치** 면적평균

14번 f0 에서 CPU 검출 입력 대비 화소별 오차 (플래시 임계 `theta_lum` = 0.10):

| GPU 축소 방식 | 평균차 | 최대차 | 임계 초과 화소 |
|---|---|---|---|
| 선형 도메인 area (원래) | 0.012748 | **0.284278** | 3.75% |
| 감마 도메인 area | 0.011564 | 0.213632 | 6.67% |
| 감마 bilinear+AA | 0.002774 | 0.116045 | 1.25% |
| **감마 bicubic+AA** | 0.005155 | **0.054322** | **0.00%** |

**최대 오차가 임계의 2~3 배**였다. 그 오차가 검출 마스크를 0.750 → 0.875 로
부풀렸고(활성 구간), 알파와 출력으로 증폭돼 안전한 원본을 위반으로 만들었다.

수정: 검출 입력을 CPU 경로 그대로 재현한다 — **감마 도메인에서 bicubic+antialias
로 축소 → uint8 → 선형화**. `area` 계열로는 어떤 도메인에서도 임계 초과 화소가
남는다. 속도 비용은 없다 (6.3~8.0 → 6.2~8.7 ms/frame).

**→ 27클립 전수: 일치 27 / 불일치 0 / 악화 0. 전 클립 PASS.**
→ `results/verify_full_27_gpu_final.txt`

원인 4 에 도달하기까지 소거한 가설들. 다시 파지 않도록 남긴다.

| 가설 | 결과 |
|---|---|

| 검출기 링(`pv._ring`) 워프 부재 | **아님.** CPU 에서 꺼도 마스크 0.6102 그대로 |
| 자기감시 가드(`gain`) 부재 | **아님.** CPU 는 가드를 꺼도(gain 0.992) 0.00 |

| `PeakValley` 로직 | **아님.** 두 구현이 논리적으로 동일 |

| uint8 재양자화 | **아님.** 단독으로는 값이 안 바뀐다 |
| "결맞은 전역 휘도 스윙" | **아님.** CPU 가 프레임간 스윙이 **더 큰데도**(0.00467 vs 0.00303) 통과한다. 심판은 전역이 아니라 국소 전이 + 창 면적으로 센다 |
| `alpha_smooth = 1.0` | **고쳐지긴 하나 채택 불가.** GPU 14번은 0.00 이 되고 단조롭지만(0.5→1.14, 0.75→0.14, 1.0→0.00), **CPU 가 0.00 → 0.26 으로 역행**하고 선명도가 광범위하게 깎인다 (01번 80%→46%, 02번 94%→65%) |

교훈: 이름이 같은 API 가 같은 일을 한다고 가정하지 말 것. 이 프로젝트에서

검출 입력(축소 도메인), 리샘플러(area 의 정의).

`GPU_FULL.md` 가 "제일 의심"한 26번 위상상관 부호는 **문제 없었다** (PASS).

또 심판 둘이 다른 말을 한다는 점을 기록해 둔다. `pse_bt1702` 로 재면 14번은

## CPU/GPU 분업은 되돌아갈 길이 아니다

"각자 잘하는 부분에서 돌리자"는 이미 `psegpu.py` 가 한 것이다 — 검출 CPU + 적용 GPU,
1080p 15.47 ms (축소 1.65 + 검출CPU 4.07 + 적용GPU 9.75). 전 GPU 판은 8.4~11.9 ms.

병목은 각 연산의 속도가 아니라 **PCIe 왕복과 프레임당 동기화**다. 검출을 CPU 에서
하려면 프레임마다 GPU 결과를 기다려 내려받고 다시 올려야 하고, 그 비용이 "CPU 가
그 연산을 더 잘한다"는 이득보다 크다. 전 GPU 판이 빠른 이유가 동기화를 1회로 줄인
것이라 분업하면 설계를 스스로 무너뜨린다.

의미 있는 분업은 층이 다르다: **실시간 A 는 GPU, 오프라인 D 는 필요할 때만.**
CPU 판은 기준자로 남긴다 — 이번 컷 버그도 CPU 대조로 잡았다.

### 실사 수집 방법 — 로그인 없이 된다

인스타 경로(`origin/seunghoon` 의 `pse_collect.py` / `pse_refetch.py`)는
`instaloader` 세션이 필요하다 — 브라우저 쿠키(`sessionid`, `csrftoken`)를 직접
꺼내야 해서 자동화할 수 없다. 그 브랜치에 **shortcode 200편이 라벨과 함께**
남아 있으니(위반 41 / 안전 152) 필요하면 되살릴 수 있다.

유튜브는 로그인이 필요 없다. `yt-dlp` 로 받되 **쇼츠를 노리지 말고 장편에서
30~70초 구간을 잘라온다** — `ytsearch` 가 주는 건 대부분 장편이라 쇼츠 길이로
거르면 표본이 안 모인다 (실측: 9편 검색에 1편).

핵심은 검색어다. **제작자가 스스로 단 경고를 검색한다** — "flash warning",

## 7. 컷 불응기 — A 필터 실사 제거율 11% → 86%

### 진단 — 실패군과 성공군을 나란히 재보니 컷이 23 배 다르다

컷 게이트가 필터를 켜지 못하게 막고 있었다. 컷마다 `prev` 가 리셋되니 시간축

40초 클립(60fps, 약 2400 프레임)에서 컷 1094 개 — **초당 25 회 장면전환**을
주장하는 셈이다. 명백한 오검출이다.
