프로젝트에서 꺼낸 검출기 파일 (2026-08-10)
===========================================

pse_analyze.py    팀 표준 검출기. BT.1702-3 기반 4채널 — LUM(휘도) / RED(채도적색)
                  / RG(적↔녹 등휘도) / BY(청↔황 등휘도) + 5초 누적(STRICT 모드).
                  다른 파일들이 여기서 SDR_PEAK, decode_linear 등을 가져다 쓴다.

pse_pattern.py    규칙적 패턴(줄무늬·격자) 검출. 2D FFT 로 지배 공간주파수·방향을
                  찾고 Gabor 로 국소 진폭·위상을 구해 실제 면적을 잰다.
                  정지 5쌍/40%, 이동 8쌍/25%, 0.5초 이상 지속 규칙.
                  → pse_analyze.py 에 아직 통합되어 있지 않다.

pse_spectrum.py   3~30Hz(및 10~20Hz) 대역 에너지 측정. 프레임률 무관.
                  "60fps 보간으로 판정만 통과시키는" 지표 게이밍을 잡는 정직성 검증용.

bt1702_detector.py  v0.1 원조. 휘도+적색 2채널만 본다. 알려진 결함 2개가 있어
                  현재는 비교·회귀 목적으로만 쓴다 (파일 상단 주석 참조).

make_testclips.py  정답을 아는 합성 클립 11편 생성 (검증용).

추가 (2026-08-10) — pse_cut.py : 빠른 컷 검출
═══════════════════════════════════════════════════════════

BT.1702 / 가이드북 2026 의 "화면 전환: 빨리 바뀌는 화면(빠른 컷 등)도
플래시 기준과 동일하게 간주" 조항 구현. 지금까지 검출기에 없던 축이다.

왜 필요한가
  LUM 채널은 밝기가 변해야 잡는다. 숏폼의 비트 맞춤 편집은 노출을 일정하게
  맞춰 놓고 장면만 빠르게 바꾸는 경우가 많아, 화면은 초당 몇 번씩 뒤집히는데
  평균 휘도는 거의 안 변해서 LUM 이 통과시킨다.

오탐 방지 4겹 (이게 이 검출기의 핵심)
  (1) 블록별 색 히스토그램 — 모션은 화면을 '이동'시키지만 색 분포는 보존
  (2) 적응 임계 — 최근 중앙값 대비 이상치인지
  (3) 일시변화 배제 — 4프레임 창 양방향. 섬광의 진입·복귀를 컷으로 안 셈
  (4) 왕복 배제 — 최근 1초 안의 샷으로 되돌아오면 컷이 아니라 플래시

검증 결과 (합성 클립 21편, 오탐·미탐 0)
  컷 전용 10편
    20_static            0컷  PASS
    21_cuts_1hz          3컷  PASS
    22_cuts_3hz          9컷  PASS   (한도 경계)
    23_cuts_6hz         18컷  FAIL   ← 휘도 동일. LUM 이 못 보는 경우
    24_cuts_10hz        30컷  FAIL
    25_whip_pan          0컷  PASS   ← 오탐 시험
    26_fast_zoom         0컷  PASS   ← 오탐 시험
    27_handheld          0컷  PASS   ← 오탐 시험
    28_flash_only_5hz    0컷  PASS
    29_scene_plus_flash  0컷  PASS   ← 섬광이 컷으로 세지지 않음
  기존 점멸/색/줄무늬 11편 — CUT 채널 전부 PASS (중복 계상 없음)

속도
  약 10.6 ms/frame (320px, 단일코어). 40초 숏폼 1편 약 12초.
  1,000편 = 단일코어 3.4시간 / 4코어 0.9시간

해석상 미확정
  규격은 "플래시 기준과 동일하게 간주"라고만 한다. 플래시 1회는 반대 방향
  변화 한 쌍이고 컷 1회는 단일 변화라, 둘의 대응이 원문에 없다.
    기본값 literal : 컷 1회 = 플래시 1회 → 초당 3회 초과면 위반
    대안   paired  : 컷 2회 = 플래시 1회 → 초당 6회 초과면 위반
  기본값이 약 2배 엄격. 결과 JSON 에 would_violate_literal / would_violate_paired
  를 둘 다 넣어 두었으니 BT.1702-3 원문 확보 후 확정할 것.

알려진 한계
  서로 다른 두 화면만 초당 여러 번 왕복하는 경우는 (4)에 의해 컷으로 세지
  않는다. 휘도와 색이 모두 맞춰진 두 장면의 왕복이면 어느 채널도 못 잡는다.
  실사에서는 거의 없지만 기록해 둔다.

사용법
  python3 make_cutclips.py cutclips     # 검증용 클립 10편 생성
  python3 pse_cut.py 영상.mp4 [...]
  python3 pse_cut.py --paired 영상.mp4  # 한도 6회/s 해석
  python3 pse_cut.py --json 영상.mp4

추가 (2026-08-10) — pse_bt1702.py : 규격 준수 단일 판정기
═══════════════════════════════════════════════════════════

질문 하나에만 답한다: 이 영상이 BT.1702 기준을 위반하는가.

구현 = 가이드북 2026 이 인용한 BT.1702 조항 그대로
  ① 플래시      초당 3회 초과 + 화면 1/4 이상 + 휘도차 20cd/m²
  ② 색상        강렬한 빨간색 플래시 (동일 빈도·면적)
  ③ 패턴        줄무늬·바둑판·고대비 무늬 (pse_pattern)
  ④ 지속·누적   5초 이상 지속
  ⑤ 화면 전환   빠른 컷도 플래시와 동일 간주 (pse_cut)
  ⑥ 프레임 간격 50Hz 9프레임 / 60Hz 10프레임

의도적으로 뺀 것 — 원추 대립축 RG / BY / RB
  등휘도 색 점멸 채널. Parra 2007 임상 근거는 있으나 BT.1702 규격에 없고,
  임계값(RG 0.10 / BY 0.20)이 실측 스윕으로 정한 경험값이라 근거가 없다.
  규격 준수 증명 도구에 근거 없는 임계를 섞으면 "왜 위반인가"에 답할 수 없다.
  색 채널이 필요하면 pse_analyze.py 를 별도로 쓰되, 결과는 "규격 위반"이
  아니라 "규격 밖 추가 위험"으로 분리 보고할 것.

⑥ 프레임 간격은 별도 조항이 아니다 (이번에 확인)
  50Hz(25fps): 25/3 = 8.33 → 올림 9프레임
  60Hz(30fps): 30/3 = 10.0 → 정확히 10프레임
  즉 ①의 3Hz 한도를 방송 프레임 수로 쓴 것. ceil(fps/3) 으로 일반화된다.

만들면서 실측으로 잡은 오탐 3건
  (1) 빠른 팬·줌·손떨림이 플래시로 잡힘
      원인: 화소별 휘도 차이를 그대로 씀. 팬에서는 밝아진 면적 0.239 /
            어두워진 면적 0.237 로 양쪽 다 25% 근처였다.
      수정: 국소 평균(폭 5%) + **순 방향성** |밝아짐 - 어두워짐| 로 판정.
            점멸 1.000 vs 팬 0.089 / 손떨림 0.037 로 깨끗이 갈린다.
  (2) 노이즈 텍스처가 줄무늬 패턴으로 잡힘
      원인: 집중도를 "피크/밴드 전체"로 재서 저주파에 편향. 블롭 노이즈가
            주기적이어서가 아니라 저주파라서 0.31 이 나왔다(임계 0.12).
      수정: **같은 반경 링 대비**로 정규화(방향 선택도). 줄무늬·격자
            0.99~1.00 vs 텍스처(쌍>=5) 최대 0.56. 임계 0.75 로 재설정.
  (3) 패턴 검출이 프레임당 90ms
      원인: Gabor 커널이 최대 101x101.
      수정: Gabor 는 위상 판별용이므로 96px 로 축소해 계산. 46ms 로 절반.
            판정 결과는 동일함을 확인.

검증 (합성 클립 21편, 오탐·미탐 0)
  점멸/색/줄무늬 11편 + 컷/모션 10편 전부 기대값 일치.
  특히 휙 돌리기·급격한 줌·손떨림 3종이 모두 적합 판정.

속도
  전체 약 66 ms/frame → 1,000편 4코어 약 5.5시간 (하룻밤)
  --no-pattern 이면 약 20 ms/frame → 1.7시간

사용법
  python3 pse_bt1702.py 영상.mp4              # 항목별 상세 리포트
  python3 pse_bt1702.py --brief 영상들*.mp4   # 한 줄 요약
  python3 pse_bt1702.py --json 영상.mp4       # 기계 판독용
  python3 pse_bt1702.py --no-pattern ...      # 빠른 스캔

정정 (2026-08-10) — Jordan, HCII 2025 반영
═══════════════════════════════════════════════════════════

근거: J. Bern Jordan, "Evaluating Conformance of Video Safety Tools for
Photosensitive Epilepsy", HCII 2025, LNCS 15780, pp.85-98.
저자는 TRACE 센터(PEAT 제작처) 소속이며 Jordan & Vanderheiden 2024
갭 분석의 같은 저자다.

이 논문이 우리 구현의 오류 3건을 잡아줬다.

────────────────────────────────────────────
① 334ms 조항 — 별도 규칙이 맞다 (이전 판단 정정)
────────────────────────────────────────────
처음에는 숫자가 겹쳐서(334ms ≈ 1/3초) 3Hz 한도를 프레임으로 바꿔 쓴
것이라 판단했으나 틀렸다. 논문 원문:

  "ITU-R 과 Ofcom 표준에는 추가 단서가 있다 — 선행엣지가 334ms 넘게
   떨어진 플래시는 안전한 것으로 본다. 다른 표준에는 이런 단서가 없다."

시퀀스를 나누는 규칙이다. ITU-R/Ofcom 이 이 지점에서 더 관대하다.
  구현: Counter.sequences() 에서 gap > 334ms 면 시퀀스 분할
  전환: analyze(..., sequence_rule=False) → WCAG/ISO/NAB-J 동작

────────────────────────────────────────────
② 장면 전환 면적은 25% 가 아니라 80%
────────────────────────────────────────────
  "NAB-J 지침에는 '장면 전환' 특별 조항이 있어 1초에 3회까지만 허용되며,
   장면 전환은 화면의 80% 로 조작적 정의된다."

  구현: pse_cut.AREA_THR 0.25 → 0.80, 격자 4x4 → 5x5 (4% granularity)
  · 초당 3회 한도는 기존 기본값(literal)이 맞았다. 논문이 "3회/초 =
    플래시 1.5회 상당"이라 명시해 literal/paired 애매함이 해소됐다.
  · 다만 이 조항의 출처는 ITU-R 이 아니라 일본 NAB-J 다. 국내 가이드북은
    BT.1702 항목으로 적어놨으므로 BT.1702-3 원문 확인이 필요하다.

────────────────────────────────────────────
③ 같은 화소가 관여해야 한다
────────────────────────────────────────────
  "제대로 된 알고리즘은 각 플래시에 같은 화소가 관여하는지도 확인해야
   한다. 화면의 25% 가 번쩍인 뒤 다른 25% 가 번쩍이면 방송 기준상
   안전으로 본다. 위험 시퀀스의 모든 플래시는 면적 임계를 넘을 만큼
   겹쳐야 한다."

  구현: 플래시마다 관여 화소 마스크(40px 폭 축소)를 보관하고, 시퀀스를
        이어갈 때 교집합을 누적. 교집합이 25% 아래로 떨어지면 시퀀스 분할.

검증 (seqclips 3편, make_seqclips.py)
  30_burst_then_gap   ITU-R 적합 / WCAG 위반  ← 334ms 규칙 작동
  31_two_regions_alt  둘 다 적합 (15플래시 → 15시퀀스)  ← 화소 동일성 작동
  32_one_region_4hz   둘 다 위반 (15플래시 → 1시퀀스)   ← 대조군

전체 검증: 합성 클립 24편(점멸·색·줄무늬 11 + 컷·모션 10 + 시퀀스 3)
          오탐·미탐 0

속도: 전체 66.9 ms/frame → 1,000편 4코어 5.6시간
      --no-pattern 20.6 ms/frame → 1.7시간

────────────────────────────────────────────
아직 반영 안 한 것 (논문이 지적한 나머지)
────────────────────────────────────────────
· 동기화 임계 — 서로 다른 영역의 선행엣지가 20ms 안쪽이어야 면적 합산.
  현재는 프레임 단위로만 본다.
· NAB-J 의 휘도 의존 시간 임계 — 밝기차 10~20%(SDR)면 2초까지 초당 5회
  허용, 이후 3회. 20% 초과면 초당 3회. 현재는 단일 임계.
· 적색의 색차 조건 — ISO/WCAG 는 채도 적색 + 비적색 상태 간 0.2 색도
  단위 차이를 요구. 현재는 채도비 0.8 만 본다.
· WCAG 의 10° 시야(416x416 px) 국소 면적 기준.

최종 (2026-08-10) — 적↔청 보조 채널 + 색차 조건
═══════════════════════════════════════════════════════════

먼저 확인한 것 — **실제 포리곤 사건은 이미 규격에 걸린다**
  적(255,0,0) 42.5 cd/m²  vs  청(0,0,255) 14.4 cd/m²
  휘도차 28.1 cd/m² > 임계 20  →  플래시 채널이 잡는다.
  게다가 적색 채도 R/(R+G+B)=1.0 이라 적색 채널도 잡는다.
  실측: porygon.mkv (12Hz 전면 적↔청 5초) → 위반 — 플래시, 적색

  즉 규격이 1997년 사건을 놓치는 것이 아니다. 진짜 구멍은
  **등휘도 + 탈채도** 적↔청이다 — 휘도가 안 변하고 채도 조건도
  안 걸려서 어느 규격도 못 잡는다.

추가 ① — 적색 채널에 색차 조건 (규격 안, 그동안 빠져 있던 것)
  근거: Jordan & Vanderheiden, ACM TACCESS 2024 —
    "적색 전환은 채도 조건 R/(R+G+B) >= 0.8 만으로 부족하고
     CIE 1976 UCS 에서 0.2 단위 이상의 색 차이를 함께 요구한다"
  구현: Δu'v' >= 0.20 을 AND 조건으로 추가. ISO 9241-391 / WCAG 조항.

추가 ② — 적↔청 교대 [보조 채널, 규격 밖]
  근거: Parra et al., Brain 2007 — 적-청 교대 유발률 **100%**
        (단색 적 88% / 청 72% / 적-녹 80% / 청-황 68%)
  임계: 원색까지의 u'v' 거리 < 0.15 로 '적 계열'/'청 계열'을 정의하고,
        그 사이 맞바꿈에 Δu'v' >= 0.2 를 요구. 면적·빈도는 규격과 동일.

  ★ **규격 판정(compliant)에 넣지 않는다.** 축 자체가 BT.1702 에도
    WCAG 에도 없기 때문이다. 결과의 supplementary 에 따로 실어
    "위반"이 아니라 "주의"로 보고한다. 이렇게 해야 규격 준수 주장이
    방어 가능하면서도 임상 신호를 잃지 않는다.

  판정을 축 부호(중점 기준)로 하면 안 된다 — 실측 u'v' 거리:
      적 0.000 / 적 탈채도 0.063 / 청 0.000 / 청 탈채도 0.068
      황 0.249 / 백·회 0.259 / 녹 0.328 / 흑 0.236(청까지)
    노랑이 적색 쪽으로, 검정이 청색 쪽으로 투영돼 오탐이 났다.
    원색 근접도로 바꾸니 0.068 vs 0.236 으로 깨끗이 갈린다.
    검정은 u'v' 분모가 0 근처라 값이 무의미하므로 밝기로 따로 막는다.
