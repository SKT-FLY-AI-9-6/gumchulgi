# 구간 저장 + 필터 토글 설계 (2026-08-21)

위험 구간만 필터본으로 보관하고, 재생 중 토글로 갈아끼운다.
`platform-mvp` 의 서버·앱에 얹는 설계다.

---

## 0. 지금과 무엇이 다른가

**현재** — 영상 전체를 필터에 통과시켜 통짜 파일 하나를 만든다.

```
videos.original_path   원본.mp4
videos.filtered_path   필터본.mp4   (전체가 필터를 거침)
재생: variant=original | filtered  로 파일을 통째로 선택
```

**변경** — 필터본에서 **필터가 실제로 건드린 구간만** 잘라 보관한다.

```
원본.mp4                 통짜 (그대로)
seg_0001.mp4 ...         조각 (위험 구간만)
video_segments 테이블    구간 인덱스
재생: 원본을 기본으로 흘리다가 구간에서만 조각으로 교체
```

---

## 1. 구간의 정의 — **필터 개입 기준**

심판의 `violation_segments`(위반 구간)가 아니라 **필터가 무장한 구간**을 쓴다.

이유: `pselive3` 는 위반 임계보다 **낮은 데서 미리 무장한다**
(`arm_count 2.0` = "3회가 되기 전에 미리 무장", `arm_area 0.20` <
표준 0.25 = "경계 직전부터 잡는다"). 심판 구간만 잘라 저장하면 그 **밖에서
필터가 바꿔놓은 부분**이 원본으로 재생되어 이음매에 점프가 생긴다.

무장 구간을 쓰면 경계에서 **필터본 = 원본**이 보장된다 —
마스크 밖은 `keff = 1` 이라 `out = prev + 1·(lin − prev) = lin` 이다.

### 구간을 어디서 얻나

| 필터 | 출처 | 상태 |
|---|---|---|
| `pselive3` | `rep["armed_segments"]` | **추가 완료** (2026-08-21) |
| `psepipe` | 이벤트 CSV / 시간 마스크 | 이미 있음 |

`pselive3` 는 `stats["armed"]` 로 개수만 세고 버렸다. `armed_at` 리스트와
`_segments()` 헬퍼를 넣어 `[[시작초, 끝초], ...]` 로 내보내게 했다.
`gap=6` 프레임 이내는 한 구간으로 잇는다 — 조각이 잘게 쪼개지면
저장·재생이 오히려 비싸진다.

## 2. ★ 핵심 제약 — GOP 정렬이 절감을 먹는다

실측 (STRONG, 2026-08-21):

| 클립 | 길이 | 무장% | 구간수 | 구간합 | **GOP 2초 정렬 후** |
|---|---|---|---|---|---|
| 2rAYFWGn4TI | 41.0s | 99.8 | 1 | 40.9s | **100%** |
| pinkvenom | 10.4s | 99.0 | 1 | 10.3s | **100%** |
| cera_khin | 16.9s | 86.0 | 2 | 14.7s | **107%** ← 통짜보다 큼 |
| Db2GfqYxNWW | 14.7s | 34.5 | 5 | 5.2s | **73%** |
| dAIxbHamViU | 31.8s | 29.0 | 9 | 9.3s | **69%** |

**전면 점멸 영상은 절감이 0 이다.** 위험할수록 위험 구간이 넓으니 구조적이다.
그리고 구간이 잘게 여럿이면 GOP 로 넓히다가 서로 붙어 절감이 사라진다.

### 대응 — 조각 전용 짧은 GOP

조각은 **원본과 같은 GOP 을 쓸 이유가 없다.** 조각 인코딩에서만 GOP 을
0.5초로 줄인다.

```
ffmpeg -i 필터본.mp4 -ss {start} -to {end} \
       -c:v libx264 -crf 18 -g {fps/2} -force_key_frames "expr:gte(t,n_forced*0.5)" \
       조각.mp4
```

효과 둘:
- **정렬 손실 감소** — 넓히는 폭이 2초에서 0.5초로
- **전환 지연 감소** — 아래 4절 참조 (안전 문제다)

대가는 비트레이트 증가(키프레임이 4배)인데, 조각이 짧아 총량 영향은 작다.

### ★ 판단 기준은 시간이 아니라 **바이트**다

실측(2026-08-21, `Db2GfqYxNWW`)이 이걸 뒤집었다:

| 클립 | 조각수 | 시간 비율 | **바이트 비율** |
|---|---|---|---|
| dAIxbHamViU | 7 | 40% | **48%** |
| Db2GfqYxNWW | 5 | 49% | **104%** ← 시간은 절반인데 용량은 더 큼 |

원인: **조각 GOP 0.5초가 키프레임을 4배로 늘린다.** 키프레임은 P프레임보다
훨씬 크고, 조각이 짧으면 그 비중이 커진다. 거기에 조각마다 무빙(moov)이 붙는다.
`dAIxbHamViU` 는 조각 평균 1.8초라 이득이 남았고, `Db2GfqYxNWW` 는 평균 1.4초 ×
5조각이라 오버헤드가 먹었다.

그래서 판단을 두 단계로 한다:

```
① 시간 비율 >= 0.95        -> 조각 만들 것도 없이 통짜
② 조각을 실제로 만들어 바이트를 잰다   (무손실 -c copy 라 싸다)
   조각합 >= 통짜 x 0.85   -> 조각 폐기, 통짜 저장
   그 미만                 -> 조각 저장
```

절단이 무손실이라 만들어 보고 재는 비용이 작다. 추정하지 말고 측정한다.

## 3. 파이프라인 변경 (워커)

```
① 검출 pse_bt1702
     ├─ 적합 → 원본만 저장, risk='safe', 끝
     ▼ 위반
② pselive3 STRONG  → 통짜 필터본 + armed_segments
③ 재판정
     ├─ 위반 → ④ base → 재판정 → 위반이면 psepipe → ...
     ▼ 적합
⑤ [신규] 조각화 판단
     ├─ 절감 < 15% → 통짜 필터본 저장 (storage_mode='full')
     ▼ 절감 충분
⑥ [신규] 구간 절단 — 조각 N개 생성 (storage_mode='segments')
⑦ [신규] 저장 전 재판정 ★
     조각을 원본에 끼운 결과를 다시 심판에게 — 적합이어야 저장
     실패하면 통짜 필터본으로 후퇴
⑧ 저장 + DB 기록
```

**⑦이 필수다.** 아키텍처 개요의 "남은 관문 3번"(실시간 경로의 저장 전 심판
재판정 안전망)이 이 설계에서는 선택이 아니다 — 조각을 이어붙인 결과가 원래
필터본과 같다는 보장이 없다(인코딩 경계, 정렬 확장분).

**필터는 여전히 영상 전체에 돌린다.** `pselive3` 는 상태를 갖는 인과 필터라
(`prev` = 직전 출력) 구간만 넣으면 차가운 상태로 시작해 출력이 달라진다.
조각화는 **필터 이후의 절단 단계**다. 연산은 안 줄고 저장만 준다.

## 4. ★ 전환 지연 — 안전 문제다

토글은 **키프레임 경계에서만** 갈아탈 수 있다. GOP 2초면 최대 2초 지연이다.

```
t=5.3s 에 사용자가 필터 ON
  → 다음 IDR t=6.0s 부터 필터본
  → 5.3~6.0s 는 원본(번쩍임)이 그대로 재생된다
```

**일반 스트리밍이면 화질이 늦게 바뀔 뿐이지만, 여기서는 0.7초를 더 노출한다.**
규격이 "1초에 3회 초과"를 위험으로 보고 5초 지속을 경고하는 도구에서
받아들일 수 없는 지연이다.

### 대응 셋 (전부 적용)

1. **기본값 ON** — `user_settings.filter_on DEFAULT 1` 로 **이미 그렇게 돼 있다.**
   끄는 건 여유 있을 때의 행동이라 지연이 무해하고, 켜는 건 급한 상황이라
   지연이 위험하다. 비대칭이므로 기본을 켜 둔다.
2. **조각 GOP 0.5초** — 최악 지연을 2.0s → 0.5s 로.
3. **선반입** — 필터 OFF 로 보는 중에도 조각을 미리 받아 둔다. 전환 시
   네트워크 대기가 없어야 지연이 GOP 한도로 끝난다.

  video_id INTEGER NOT NULL REFERENCES videos(id),

  start_s  REAL NOT NULL,
  end_s    REAL NOT NULL,

`filter_level`(`strong|base`)은 이미 있다 — `psepipe` 를 파이프라인에 남기면
`'pipe'` 를 값에 추가해야 한다.

## 6. 재생 — ★ 방식 미결, 팀 결정 필요

### 전제가 하나 틀렸었다

이 절은 원래 MSE(Media Source Extensions)로 소스 버퍼를 조립하는 안을 적었다.
**앱이 Flutter 이고 `video_player: ^2.9.2` 를 쓰므로 MSE 를 못 쓴다** —
그 패키지는 ExoPlayer(안드로이드) / AVPlayer(iOS) 를 감싼 것이고 URL 재생만
노출한다. 커스텀 미디어 소스나 버퍼 조립 API 가 없다.

그래서 선택지가 셋이고, **결정에 실측이 필요하다.**

### A. HLS 플레이리스트 두 벌

원본과 조각을 같은 타임라인의 HLS 세그먼트로 노출하고 플레이리스트만 다르게.

```
filter_off.m3u8   전부 원본 세그먼트
filter_on.m3u8    위험 구간만 조각으로 치환
```

`video_player` 가 HLS 를 네이티브 지원하므로 재생 자체는 된다.
원본은 통짜 파일에 `EXT-X-BYTERANGE` 로 참조하면 추가 저장이 없다.

- **문제: 전환이 끊긴다.** 플레이리스트를 바꾸려면 컨트롤러를 새로 만들어야
  하고, 그러면 로딩·시킹이 눈에 보인다. **GOP 지연(0.5초)보다 나쁠 수 있다.**
  실기기에서 재생성 비용을 재봐야 안다.
- 서버 작업: m3u8 생성. 조각을 HLS 세그먼트 격자에 맞춰야 한다.

### B. 플레이어 두 개 동기 재생

원본용·필터본용 컨트롤러를 동시에 돌리고 표시만 바꾼다.

- **전환이 즉시다** — 이 도구에서 전환 지연은 "화질이 늦게 바뀜"이 아니라
  **"번쩍임에 더 노출됨"** 이라 값이 크다 (4절 참조).
- 문제: 대역폭·디코드 2배. 모바일 동시 디코드가 버티는지 실측 필요.
- 구간 저장의 이점이 사라진다 — 필터본 통짜를 받아야 하므로.
  구간 저장을 살리려면 조각만 미리 받아 두고 그 구간에서만 두 번째
  컨트롤러를 띄우는 변형이 있다(복잡도 증가).

### C. 필터 항상 켜짐 — 토글을 실시간 전환에서 뺀다

`filter_on` 소스 하나만 재생한다. 토글은 "설정 변경 후 다시 재생"으로.

- **전환 문제가 아예 없다.** 구현이 가장 단순하고 구간 저장 이점을 그대로 쓴다.
- 근거: `user_settings.filter_on` 기본값이 이미 1 이고, **끄는 것은 드문 행동**
  이다. 급한 쪽(켜기)에 지연이 없다는 것이 4절의 비대칭 논리와 맞는다.
- 문제: 시연에서 "켜고 끄며 비교" 하는 그림이 안 나온다. 발표 요구와 충돌.

### 결정에 필요한 실측 (스파이크 반나절)

1. `video_player` 컨트롤러 재생성 체감 지연 — A 의 가부가 여기서 갈린다
2. 모바일 동시 디코드 2 스트림 — B 의 가부
3. 대상 기기에서 HLS 세그먼트 전환 시 프레임 드롭

### 어느 쪽이든 공통

```
GET /videos/{id}/manifest?filter=on|off
```

```json
{"duration_s": 31.8, "storage_mode": "segments",
 "original": "/videos/12/stream?variant=original",
 "segments": [{"start_s": 0.9, "end_s": 1.6, "url": "/videos/12/seg/0"},
              {"start_s": 2.6, "end_s": 5.1, "url": "/videos/12/seg/1"}]}
```

`storage_mode='full'` 이면 `segments` 는 빈 배열이고 클라이언트는 기존처럼
`variant=filtered` 통짜를 쓴다 — **어느 방식을 고르든 이 폴백은 유지해야 한다.**

`watch_events.variant` 는 이미 `original|filtered` 를 기록한다.
구간 재생 중에는 `filtered` 로 집계한다.

## 7. 엣지 케이스

| 상황 | 처리 |
|---|---|
| 원본이 적합 | 조각 없음. `risk='safe'`, 토글이 무의미하므로 UI 에서 숨김 |
| 보정 실패 (`uncorrected`) | 조각 없음. 경고 표시 + 편집자 CSV. 토글해도 원본 |
| 조각이 영상 전체를 덮음 | `storage_mode='full'` 로 통짜 저장 |
| 구간이 매우 잘게 많음 | `gap` 을 키워 병합 (현재 6프레임) |
| 재생 중 시킹 | 목표 시점이 구간 안이면 그 조각의 IDR 부터 |
| 조각 다운로드 실패 | **원본으로 폴백하지 말 것** — 위험 구간이다. 재시도하거나 정지 |

마지막 항목이 중요하다. 조각을 못 받았을 때 원본을 트는 것은 **필터가 켜져
있는데 위험 구간을 그대로 보여주는 것**이다. 안전 방향의 폴백은 "정지" 다.

## 8. 구현 순서

1. **`pselive3.armed_segments`** — 완료 (2026-08-21)
2. **조각화 스크립트** — 필터본 + 구간 → 조각 N개. `-force_key_frames` 로
   경계 IDR 강제, `-c copy` 로 무손실 절단이 가능하면 그쪽 우선
3. **⑦ 저장 전 재판정** — 조각을 끼운 결과를 `pse_bt1702` 로. **필수**
4. DB 마이그레이션 (5절)
5. `/manifest` API
6. 앱 MSE 재생 + 선반입
7. 조각 GOP 0.5초 튜닝 — 지연과 용량의 균형 실측

1~3 은 서버 없이 로컬에서 검증 가능하다. 4 부터 `platform-mvp` 를 건드린다.

## 9. 미결

- **`psepipe` 가 파이프라인에 남는가** — `e20c33b` 확정 문구가 `strong → base`
  까지만 적었고 `psepipe` 를 언급하지 않는다. 남는다면 `filter_level` 에
  `'pipe'` 추가와 구간 출처 분기(이벤트 CSV)가 필요하다.
- **`base` 제거 여부** — σ2 출력의 잔상이 시연 기준으로 나쁘다는 지적이 있다.
  빼면 적합 187 → 185, "퇴보 0" 보장이 깨진다. `psepipe` 로 대체 가능한지는
  폴백 5편만 돌리면 확인된다.
- **바이트 임계 0.85** — 조각화 여부의 경계. 실측 소수 기준의 임시값이라
  코퍼스를 늘려 정할 것.
- **조각 GOP 을 클립마다 정할 것인가** — 조각이 길면 0.5초로 이득이 남지만,
  짧고 많으면 키프레임 오버헤드가 커진다. 1초로 올리면 용량은 줄고 전환
  지연은 는다(안전과의 교환). 조각 평균 길이로 자동 선택하는 안이 있다.
