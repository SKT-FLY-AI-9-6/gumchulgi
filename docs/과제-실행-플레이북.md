# 과제 실행 플레이북 — 전 과정 단계별 기술과 실행 방법 (2026-08-21)

남은 과제 전부에 대해 **지금 쓸 수 있는 기술**(저장소 안 + 밖)과 **실행
방법**(명령 순서)을 적는다. 전체 과정은 제품 파이프라인 순서로 나눈다:
검출 → 보정 → 검증·측정 → 저장·전송 → 재생·표시 → 성능·확장.
학습 관점의 같은 지도는 `영상처리-견습-로드맵.md` 에 있다 — 이 문서는 실행 편이다.

---

## 0. 검토 — 전 과정 어디까지 왔고, 무엇이 남았나

| 단계 | 현재 상태 | 남은 과제 |
|---|---|---|
| 1 검출 | pse_bt1702 정본, trace 138편 대조 — **완성** | 위반 코퍼스 확장, 교차검증 지속 |
| 2 보정 | 3종(pselive3·psegpu_full·psepipe), 플래시·적색 해결 | **패턴 축 · 화면전환 축 · slew_chroma 색 보존** |
| 3 검증·측정 | seam·spectrum·regress 체계 완비 | σ8 실사, psepipe 폴백 5편, 기본값 승격 회귀 |
| 4 저장·전송 | 조각화 2~3단계 **검증 완료** (설계 10절) | segstore 커밋, 4~7단계, playlist.m3u8 |
| 5 재생·표시 | 통짜 스트리밍만 | 앱 HLS 전환, 필터 토글 |
| 6 성능·확장 | GPU 5.0~10.9배, armed_segments 이식 완료 | verify_full 악화 0, 가드 이식, 실시간 안전망 |

### 이번 검토에서 발견한 정합성 문제 3건 — 코드보다 먼저 고칠 것

1. **`segstore.py` 가 저장소에 없다.** 구간저장 설계 10절이 "2~3단계를 끝까지
   돌렸다"며 검증 근거로 인용하는 `scratchpad/segstore.py` 가 어디에도 커밋돼
   있지 않다. 지금 이 검증은 재현 불가능하다. **최우선 커밋 대상.**
2. **구간저장 8절이 6절과 어긋난다.** 8절 구현 순서의 5~6단계가 "`/manifest`
   API·앱 MSE 재생"인데, 이는 6절 재작성(HLS 전제조건 확정, 91a51fa) **이전**
   문구다. 6절이 확정한 대로 `playlist.m3u8` API·HLS 재생으로 읽고 8절을
   갱신해야 한다 — 지금 상태로는 새로 합류한 사람이 MSE 를 구현한다.
3. **승격 회귀의 후보가 문서마다 다르다.** 아키텍처-개요 7절은 "base vs
   STRONG", GPU 가이드 5절의 실제 명령은 `net_directional=True,detail_sigma=32`.
   게다가 작업기록-0821 3절 요인설계가 **"net 은 오차 수준(±1.3), 일하는 것은
   σ"** 를 실측했다. GPU 노트북 시간을 쓰기 전에 후보 재정의부터 하라
   (아래 3단계 참조).

## 1단계 — 검출: 완성. 운용과 코퍼스만 남았다

**기술 (전부 저장소 안)** — `tier.py`(3단계 판정: 위반/여백없음/안전),
`margin.py`(규칙별 측정/한도/여백 %), `pse_migraine.py`(WARN 전용 편두통 축).

**실행**
```bash
cd psepipe_v3_seam
python tier.py 영상.mp4              # 판정. 여러 편: *.mp4, 급하면 --no-pattern
python margin.py 영상.mp4            # 어느 축이 얼마나 넘는지 + 적색 채도 분포
```

**남은 과제 — 위반 코퍼스 확장.** 실측이 이미 전략을 정해줬다(작업기록 8절):
검색어 기반 0/16, 게임 0/28, **직접 선별 쇼츠·릴스 6/10.** 게임이 안 걸리는
이유(면적은 넘치고 빈도 3회/s 가 모자람)를 뒤집으면 수집 기준이 된다 —
**시스템적 반복**(리듬게임 비트, 탄막 피격, 의도적 스트로브, 콘서트 조명)만
노린다.

**숨은 자료·지름길**
- `yt-dlp -f "bv*[height<=480]"` — 판정은 320px 분석이라 저화질로 받아도 된다.
  다운로드 시간이 1/5 이 된다
- **PEAT**(Trace Center, 무료) — Harding FPA 의 무료 대안. `IRIS_교차검증`
  다음 상대로 제3자 대조에 쓸 것
- 후보를 통째로 다 보지 말고 `tier.py --no-pattern` 으로 1차 거른 뒤
  위반·여백없음만 정밀 판정 — 검출 시간의 70%가 패턴이다(사용법 5절)

## 2단계 — 보정: 미해결 3과제의 기술과 실행

### 과제 A — 패턴 축 ③ (pselive3 "항상 실패", 작업기록 1절)

원인은 명확하다: pselive3 는 화소별 **시간** 연산뿐이라 공간 구조(줄무늬·
바둑판)의 대비를 낮출 수단이 없다. 쓸 수 있는 기술, 만만한 순서로:

1. **psepipe 작동기 B — 이미 있다.** 패턴 대비 감쇠가 사다리에 구현돼 있다.
   먼저 이것 단독 성능부터 실측하라. 부족분이 확인돼야 신규 개발 근거가 된다.
2. **로컬 대비 감쇠** — 위반 bbox 안에서 `out = μ_local + β·(in − μ_local)`
   (β<1, μ_local 은 가우시안 로컬 평균). 경계 헤일로가 생기면 가우시안 대신
   **guided filter**(He et al., `cv2.ximgproc.guidedFilter`)로 경계 보존.
3. **공간 주파수 선택 감쇠** — 위험 대역만 노린다. Wilkins 1984 가 1~8cpd
   (시야각당 주기)를 위험 대역으로 실측했고, **cpd 환산 코드는
   `pse_migraine.py` M1 에 이미 있다**(시청 거리 가정 포함). FFT 밴드스톱
   또는 Gabor 응답 기반 감쇠로 그 대역만 누르면 개입이 최소가 된다.
4. 감쇠가 아니라 **디포커스**가 허용되는 연출이면 위반 영역 한정 블러가
   가장 값싸다 — 단 pselive3 의 "블러 원리적 불가" 성질을 잃는 경로이므로
   psepipe 쪽 작동기로만.

**실행**
```bash
python legacy_detectors/make_testclips.py testclips   # 04 정지 패턴, 14 흐르는 줄무늬 포함
cd psepipe_v3_seam
python psepipe.py 패턴클립.mp4 out.mp4                # 사다리(작동기 B 포함) 단독 실측
python tier.py out.mp4                                # 재판정
python seam.py 패턴클립.mp4 out.mp4                   # 부작용(헤일로·펌핑) 동시 측정
```
합성에서 작동기 B 가 뚫리는 지점이 확인되면, 그 클립을 고정하고 2→3 순서로
후보를 실험한다. 판정은 pse_bt1702, 부작용은 seam — 기존 관행 그대로.

### 과제 B — 화면전환 축 ⑤ (컷 5/s 이상, STRONG 도 못 푼다 — 작업기록 4절)

1. **psepipe 디졸브 — 이미 있고, 이것이 정식 해법이다.**
   `python psepipe.py in.mp4 out.mp4 --dissolve 5` (사용법 3c). 컷 경계를
   크로스페이드로 바꿔 "빠른 컷 = 플래시" 성립 자체를 깬다. 편집 의도가
   바뀌는 개입이므로 확인 후 사용이라는 단서까지 이미 문서화돼 있다.
2. σ2 강한 억제 — 실사에서 컷을 실제로 푼 유일한 설정이지만(작업기록 4절)
   잔상 대가가 커서 시연 기준 나쁘다는 지적이 있다. 폴백으로만.
3. **컷 검출 고도화** — pselive3 의 NCC 컷 검출과 교차검증할 외부 기술:
   PySceneDetect(ContentDetector, 고전·가벼움), TransNetV2(신경망 샷 경계
   검출, 공개 가중치). 컷 위치가 정확해질수록 디졸브 개입 폭이 준다.

**실행** — 화면전환 잔존 실측 2편이 이미 지정돼 있다:
```bash
python psepipe.py ngb5jLR1_pg.mp4 out1.mp4 --dissolve 5
python psepipe.py EdbIgJtgjSA.mp4 out2.mp4 --dissolve 5
python tier.py out1.mp4 out2.mp4      # 컷/s 이 3 이하로 내려오는가
```

### 과제 C — slew_chroma 색 보존 (작업기록 2절 ★발견의 마무리)

색 상한을 3배 풀어도 억제 수치가 소수점까지 동일했다 — 남은 것은 등휘도
조건 검증뿐이다. 색 항이 실제로 일하는 유일한 조건이 합성 06/07 이다.

**실행** (몇 분짜리 실험이다 — 가장 먼저 끝내라)
```bash
cd psepipe_v3_seam
# 06_iso_red_blue_sat / 07_iso_red_blue_desat 에 색 상한 0.030 을 걸고
python pselive3.py ../testclips/06_iso_red_blue_sat.mp4 --video out06.mp4 --slewc 0.030
python pselive3.py ../testclips/07_iso_red_blue_desat.mp4 --video out07.mp4 --slewc 0.030
python margin.py out06.mp4 out07.mp4   # ②적색 축이 여전히 잡히는지
```
통과하면 기본값 0.010 → 0.030 상향의 근거가 완성된다(억제 불변·채도 +7%p·
잔상 −26% 는 이미 실측됨). 통과 못 하면 다음 기술로: 절대량 상한 대신
**Δu′v′ 기반 상대 상한** 유도 — 적색 규칙이 이미 Δu′v′ 0.2 로 정의돼 있으므로
같은 좌표계에서 `S_chr = safety × 0.2 / n_look` 꼴로 판정기에서 유도할 수
있다. 휘도 상한 S 가 그렇게 유도된 것과 정확히 같은 방법이다.

## 3단계 — 검증·측정: 결정을 기다리는 실험 3건

**기술** — `validation/regress_ab.py`(`--base`/`--cand` 설정 비교, 악화·퇴보
카운트), `seam.py`(이질감 5축), `pse_spectrum.py`(3~30Hz 대역 에너지),
`compare_ad.py`(A vs D 공정 비교). 전부 저장소 안에 있다.

1. **psepipe 폴백 5편** — 한 실험으로 미결 2건(설계 9절: psepipe 잔류 여부,
   base 제거 여부)이 동시에 풀린다. base 가 못 고친 5편에 psepipe 를 돌려
   대체 가능하면 σ2 잔상 문제가 사다리에서 사라진다:
   ```bash
   python psepipe.py 폴백클립.mp4 out.mp4 && python tier.py out.mp4
   python seam.py 폴백클립.mp4 out.mp4     # 잔상이 base(σ2)보다 나은지
   ```
2. **σ8 실사 확인** — seunghoon 스윕(360p·잔상 미측정)의 구멍 메우기.
   σ8 이 헤일로 이득 65% 를 가져가는 가성비 지점인지:
   ```bash
   cd validation
   python regress_ab.py 실사3편/*.mp4 --cand "detail_sigma=8" --csv sigma8.csv
   ```
3. **기본값 승격 회귀** — 0절 정합성 3번을 먼저 정리할 것. 요인설계 실측
   (σ 가 일하고 net 은 오차 수준)에 따라 후보를 `detail_sigma` 중심으로
   재정의한 뒤, GPU 노트북에서 가이드 5절의 2줄 (합성 27 + 실사 209편,
   `--gpu`, 악화 0·퇴보 0 관문). σ 는 펌핑과의 교환임이 확인됐으므로
   (작업기록 3절) 회귀 CSV 에서 펌핑 열을 반드시 눈으로 볼 것.

**지름길** — 스윕에서 어떤 항을 3배 바꿨는데 목적 수치가 소수점까지 같으면
그 항은 일을 안 하고 있다(slew_chroma 발견의 패턴 — 재사용하라). 두 결과표
비교 전에 반드시: **기준선(심판·인코딩·설정)이 같은가?** psecore 채널 초와
bt1702 6축은 부분집합 관계도 아니다(작업기록 7절 — 발표 최대 리스크).

## 4단계 — 저장·전송: 검증은 끝났고 제품화가 남았다

조각화(2단계)+저장 전 재판정(3단계)은 이미 통과했다(설계 10절 — 조각
이어붙임 판정 적합, 용량 40~48%). 남은 실행:

0. **segstore.py 를 `server/worker/` 로 커밋** (0절 1번). 검증에 쓴 코드가
   제품 코드가 되는 것이 맞다 — `worker/segments.py`(격자 정렬·후퇴 조건,
   테스트 7건 있음)와 합쳐 한 모듈로.
1. **DB 마이그레이션** — `video_segments` 테이블 (설계 5절).
2. **`GET /videos/{id}/playlist.m3u8?filter=on|off`** (설계 6절 확정안).
   `filter=off` 는 통짜 원본을 `EXT-X-BYTERANGE` 로 참조(추가 저장 0),
   `filter=on` 은 원본 바이트레인지와 조각 URL 을 타임라인 순으로 배열.
   `storage_mode='full'` 폴백 유지.
3. 앱 HLS 전환(5단계) **후에야** 통짜 filtered.mp4 삭제 — 순서 엄수.

**기술 (핵심 명령)**
```bash
# 원본·필터본을 같은 키프레임 격자(0.5s)로 인코딩 — 조각 경계가 IDR 이 된다
ffmpeg -i in.mp4 -c:v libx264 -crf 16 -force_key_frames "expr:gte(t,n_forced*0.5)" out.mp4
# 무손실 절단 (경계가 키프레임일 때만 성립)
ffmpeg -ss 시작 -to 끝 -i filtered.mp4 -c copy seg_0001.mp4
# 경계가 정말 IDR 인지 검사
ffprobe -show_frames -show_entries frame=pict_type,pts_time seg_0001.mp4 | head
```
미결 튜닝 2건도 실측으로 정한다: `gap` 6→15프레임(19조각 파편화 실측 근거,
설계 9절), 조각 GOP 0.5s vs 1s(용량↔전환지연 교환).

**숨은 자료·지름길** — RFC 8216(HLS 원문, 짧고 읽힌다), **hls.js 데모
페이지**(URL 만 넣으면 세그먼트 로딩·에러 즉석 확인 — 앱 붙이기 전 디버깅은
전부 여기서), Bento4 `mp4info`(상자 구조 해부), `ffprobe -show_packets` 로
바이트레인지 오프셋 추출. 이음매 문제의 대부분은 키프레임 비정렬이다.

## 5단계 — 재생·표시: 앱이 조립하게 한다

**기술** — Flutter `video_player` 는 ExoPlayer/AVPlayer 래퍼라 URL 재생만
되지만, **둘 다 HLS 네이티브 지원**이라 `playlist.m3u8` URL 을 그대로 먹는다.
설계 6절이 HLS 를 전제조건으로 못 박은 이유가 이것이다.

**실행**
1. 서버 playlist 를 hls.js 데모로 먼저 검증(4단계) — 앱 디버깅과 분리.
2. 앱: `VideoPlayerController.networkUrl(...playlist.m3u8?filter=on&토큰)`.
   웹 빌드는 기존 `stream?variant=` 폴백 유지(설계 6절).
3. 토글 = 컨트롤러 재생성 + `seekTo(현재 위치)`. 전환 지연이 거슬리면 조각
   GOP 튜닝(4단계 미결)과 함께 실측.
4. 완료 후 `pselive3` 의 지연 0 설계 자산을 기억할 것 — 미리보기·온디바이스
   요구가 오면 그대로 꺼내 쓴다(아키텍처 5절).

## 6단계 — 성능·확장: GPU 승격과 실시간 대비

**현재** — psegpu_full 5.0~10.9배, `armed_segments` 이식 완료(구간 시작점
소수점 일치). 남은 셋:

1. **verify_full 악화 0** — 승격 전제조건:
   ```bash
   python verify_full.py --quick        # 빠른 확인, 전체는 옵션 없이
   ```
2. **가드 이식** — `pselive3._guard`(조건부)를 텐서로. 업로드형에서는 급하지
   않지만(209편 가드 없이 악화 0) **실시간 경로의 전제조건**이다 — 클립
   재판정을 못 하므로. 이식 모범은 이미 있다: armed_segments 이식이
   "이미 하는 float() 동기화 값을 재활용해 추가 동기화 0"으로 들어갔다
   (설계 9절). 가드도 같은 원칙 — GPU→CPU 동기화를 새로 만들지 말 것.
3. **실시간 안전망** — 저장 전 `pse_bt1702` 재판정 한 줄 규칙(아키텍처 7절).
   구간저장 3단계(저장 전 재판정)와 같은 훅이므로 segstore 커밋 때 함께.

**지름길** — GPU 이식 검증은 언제나 성능보다 **CPU 판과의 프레임 일치**부터
(`verify_full` 이 그 도구). 끝점 불일치가 나오면 armed_segments 때처럼
부동소수 경계 프레임인지부터 의심.
